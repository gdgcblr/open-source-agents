# TCP vs. UDP for Backend Engineers

Both TCP and UDP are transport-layer protocols that move data between applications over IP. The core trade-off is **reliability and ordering** (TCP) versus **low overhead and speed** (UDP).

## Quick Comparison

| Aspect | TCP | UDP |
|---|---|---|
| Connection | Connection-oriented (3-way handshake) | Connectionless (send and go) |
| Reliability | Guaranteed delivery via ACKs and retransmission | No guarantees; packets can be lost |
| Ordering | In-order delivery | No ordering; packets can arrive out of order |
| Flow control | Yes (receive window) | No |
| Congestion control | Yes (slow start, backoff) | No (the application must handle it) |
| Data model | Byte stream (no message boundaries) | Discrete datagrams (message boundaries preserved) |
| Header size | 20+ bytes | 8 bytes |
| Overhead | Higher (handshakes, ACKs, state) | Lower |
| Latency | Higher under loss (head-of-line blocking) | Lower, more predictable |
| Broadcast/multicast | Not supported | Supported |

## How TCP Works

1. **Handshake:** The client sends SYN, the server replies SYN-ACK, and the client confirms with ACK. This costs one round trip before data flows.
2. **Reliability:** Each byte has a sequence number. The receiver acknowledges what it got, and the sender retransmits anything unacknowledged.
3. **Ordering:** The receiver reassembles segments into the original order before handing data to the application.
4. **Flow and congestion control:** The receiver advertises a window to avoid being overwhelmed, and the sender backs off when the network shows signs of congestion.
5. **Teardown:** A FIN/ACK exchange closes the connection, and sockets linger in `TIME_WAIT` afterward.

## How UDP Works

UDP adds only source/destination ports, a length, and a checksum on top of IP. Each `sendto` produces one datagram, and each `recvfrom` returns one whole datagram. If it's lost, nothing retransmits it unless your application does.

## When to Use Each

**Use TCP for:**
- HTTP/1.1 and HTTP/2 APIs
- Databases (PostgreSQL, MySQL, Redis)
- Message queues where delivery matters
- File transfers and anything where a corrupted or missing byte is unacceptable
- Most default choices in backend services

**Use UDP for:**
- DNS queries (small, request-response)
- Real-time media: VoIP, video calls, live streaming
- Online games and telemetry where stale data is worse than lost data
- Service discovery and broadcasts (mDNS, DHCP)
- Metrics and logs where occasional loss is acceptable (StatsD, syslog over UDP)
- Building custom protocols that need control over retransmission

**Modern note:** HTTP/3 and QUIC run over UDP and implement reliability, ordering, and congestion control in user space. This avoids TCP head-of-line blocking across streams and speeds up connection setup. Many modern systems use UDP as a foundation and add only the guarantees they need.

## Practical Pitfalls

- **TCP is a byte stream, not a message stream.** A single `read()` may return part of a message or several messages together. Use length-prefixed framing or a delimiter, and loop until you have a complete message.
- **UDP doesn't mean "fast and safe to ignore errors."** Packets can be lost, duplicated, reordered, or exceed the MTL (path MTU). Keep datagrams below roughly 1200–1400 bytes to avoid IP fragmentation.
- **Idempotency matters.** Retries on TCP can still double-apply a request if the connection drops after the server processed it. Design APIs with idempotency keys.
- **Connection churn is expensive.** Open connections are costly, so use connection pooling and keep-alives. Watch for `TIME_WAIT` buildup on high-traffic clients.
- **Timeouts and deadlines are your responsibility.** Set them explicitly at every layer. TCP's retransmission can stall for minutes by default on some systems.
- **Half-closed connections happen.** Handle EOF and `RST` errors, and treat "connection reset by peer" as a normal event.
- **Load balancers and NAT treat them differently.** UDP state (for NAT mappings) times out quickly, so long-lived UDP flows often need keepalive packets.
- **Debugging differs.** TCP issues show up as retransmissions and resets in `tcpdump` or `ss -ti`. UDP loss is only visible through application-level sequence numbers or metrics.

## Rule of Thumb

Start with TCP. Move to UDP only when you have a specific reason, such as latency-sensitive real-time data, a need for broadcast, or a tolerance for loss that makes retransmission harmful. If you find yourself reimplementing ordering, acknowledgments, and retries on top of UDP, consider whether QUIC or TCP would serve you better.
